# PDK Startup and Device-Script Integration

## Purpose
Specifies what open-PDK support files expect from the layout editor and what the editor does on their behalf. This covers sky130A/B, gf180mcuA-D, IHP sg13g2 and other PDKs generated by open_pdks. These PDKs ship two kinds of file:
- a startup file `<pdk>/libs.tech/magic/<pdk>.magicrc`;
- a device-generator script `<pdk>/libs.tech/magic/<pdk>.tcl`, built on the gencell framework (see `pcell-toolkit`). It sources per-family part files `<pdk>-<part>.tcl` from its own directory. For sky130 and gf180mcu, the installed `<pdk>.tcl` is the template followed by the shared helper file `common/pdk.tcl` (appended at install time). IHP sg13g2 ships its own copy of those helpers in `ihp-sg13g2-util.tcl`.

This capability specifies:
- the startup ordering and command-line file handling these scripts rely on;
- the script variables and environment they read and write;
- the command surface their generators use;
- automatic technology discovery from layout files;
- the PDK path conventions in saved files.

Result formats are specified in `scripting-api`. The full startup-file search order is owned by capability `app-startup`. The PDK file contents described here are not part of the Magic tree. They were verified against open_pdks @ `c6df28c1` (sky130, gf180mcu templates and `common/pdk.tcl`) and IHP-Open-PDK @ `5e6d592e` (`ihp-sg13g2/libs.tech/magic`); see Q-SCRIPT-9. PDK references have the form `(PDK ref: <repo> <path>:<line>)`, where `open_pdks` paths are relative to the repository root and `IHP` paths are relative to `ihp-sg13g2/libs.tech/magic/`. The templates contain preprocessor tokens (`TECHNAME`, `STAGING_PATH`, `MAGIC_CURRENT`, `#ifdef`) that open_pdks replaces at install time: `TECHNAME` becomes the PDK variant name (for example `sky130A`), and `MAGIC_CURRENT` becomes `libs.tech/magic`.

## Requirements

### Requirement: Script-host startup sequence
In the scripting build, startup SHALL proceed in this order:
1. Load the engine extension.
2. Define the batch-mode console stubs and the `irsim`/`xcircuit`/`netgen`/`echo` helpers.
3. Parse the command line (next requirement).
4. If the GUI wrapper is enabled, source the wrapper and insert `-nowindow` as the first engine argument.
5. Run engine initialization with the remaining arguments. On failure, exit with status 1.
6. Source each of these optional scripts that exists in `$CAD_ROOT/magic/tcl/`, setting `Opts(<name>)=0` after each: `padlist.tcl`, `tools.tcl`, `mazeroute.tcl`, `toolkit.tcl`, `readspice.tcl`.
7. Set `auto_noexec`. Install the collision renames and the unknown handler. Import the commands globally.
8. Run the startup files (`magic::startup`). PDK `.magicrc` files execute at this point, after `toolkit.tcl` and `readspice.tcl` are available and before any layout window exists in wrapper mode.
9. Withdraw the toolkit root window if its title begins with `wish` or `magicexec`.
10. Save `drc status` and turn DRC off.
11. Open the initial window, unless a startup file already created a layout window. In wrapper mode with a display, use `openwrapper` and `techmanager initall`. In NULL graphics, use `openwindow`. Then load the command-line files (see "Command-line file arguments").
12. Print `Using technology "<tech name>", version <first element of tech version>`.
13. If no box exists, set the box to 0 0 1 1. Run `view` if files were given, else `view -9 -9 10 10`.
14. Run `crash recover` if `-r` was given.
15. Unset the temporary globals `celllist`, `nlist` and `do_recover`. Turn DRC back on if it was on.

See Q-SCRIPT-33 for `techmanager initall`.
Compatibility: behavioral

### Requirement: Command-line options in the script host
The script host SHALL classify each argument with the following regular expressions, in order:

| Pattern | Action |
|---|---|
| `^-now(rap)?(per)?$` | disable the wrapper |
| `^-dnull` | disable the wrapper and pass the argument through |
| `^-r(e)?(cover)?$` | request crash recovery |
| `^-rc(file)?$` | pass through with the next argument |
| `^-d`, `^-g`, `^-m`, `^-i`, `^-T` | pass through with the next argument |
| `^-F` | pass through with the next two arguments |
| `^--version` | print `<version>.<revision>` and exit 0 |
| `^--commit` | print the commit id and exit 0 |
| `^--prefix` | print `$CAD_ROOT` and exit 0 |
| `^-D`, `^-n*` | pass through. Because `n*` may match zero characters, `^-n*` matches every remaining argument that begins with `-`, so unknown options are never treated as files |
| anything else | a file to load, also passed through |

Because the patterns are tested in this order, `-noc...` (console) is consumed by the launcher before this table applies, and `-rcfile` is matched by the `^-rc(file)?$` row and not as recovery. See Q-SCRIPT-37 for the ordering hazard with `-r`.
Compatibility: behavioral

(Magic ref: tcltk/magic.tcl.in:158-237, tcltk/magic.sh.in:33-72)

### Requirement: Command-line file arguments
Each file argument SHALL be handled by its extension:

| Extension | Action |
|---|---|
| `.lef`, `.LEF` | `lef read` |
| `.def`, `.DEF` | `def read` |
| `.gds`, `.GDS`, `.gds2`, `.GDS2`, `.gdsii`, `.GDSII` | `gds read` |
| `.cif`, `.CIF` | `cif read` |
| `.tcl` | `source` |
| `.mag` or none | `load` |
| `.gz` | wrapper mode only: an inner `.gds` gives `gds read`, an inner `.mag` gives `load`, anything else prints `only compressed .mag and .gds are handled.` |
| other | print `don't know how to load file <f>` on stderr |

In wrapper mode, every non-empty extension other than `.gz` first prints `Handling file entry <f> extension <ext>`. In NULL graphics, every file prints `handling file entry <f> extension <ext>`, and `.gz` falls into "other". Files SHALL be processed in command-line order after the startup files.

### Requirement: Startup files are scripts
Every startup file SHALL be evaluated as a script at global scope. This includes the system pre-startup file `$CAD_ROOT/magic/sys/.initrc`, the system file `$CAD_ROOT/magic/sys/.magicrc`, the user file, the project file, and a file given by `-rcfile`. Script control flow (`if`, `catch`, `proc`, variables, `source`, `$env(...)`) is therefore available to PDK `.magicrc` files. An error in a file SHALL stop that file at the error and print `Error parsing <kind> "<file>": <message>`. Startup then continues with the next file. The system file SHALL set `GND` to `gnd!` and `VDD` to `vdd!`, and SHALL run the tool setup when `tools.tcl` was loaded. A later startup file can therefore override `VDD`, `GND` and `SUB`.
Compatibility: behavioral

### Requirement: PDK startup file contract
The editor SHALL execute each PDK `.magicrc` listed below unchanged, giving every statement the semantics specified in `scripting-api` and the command capabilities. The three verified startup files perform these steps, in this order (a dash means the step is absent):

| # | Step | sky130A/B | gf180mcuA-D | ihp-sg13g2 |
|---|---|---|---|---|
| 1 | Banner `puts stdout "Sourcing design .magicrc for technology <tech> ..."` | yes | yes | yes |
| 2 | `set scalefac [tech lambda]`; if `[lindex $scalefac 1] < D`, run `scalegrid 1 D` | D = 2 | D = 10 | D = 2 |
| 3 | `drc euclidean on` | yes | yes | yes |
| 4 | `catch {random seed}` (time-based seed; see Q-SCRIPT-44) | yes | yes | yes |
| 5 | `ext2spice scale off` | yes | — | yes |
| 6 | `if {[catch {set PDK_ROOT [file nativename $env(PDK_ROOT)]}]} {set PDK_ROOT <install root>}` | yes | yes | — (commented out) |
| 7 | `tech load <file>` | `$PDK_ROOT/<tech>/libs.tech/magic/<tech>.tech` (the full-tech variant loads `<tech>-F.tech`) | `$PDK_ROOT/<tech>/libs.tech/magic/<tech>.tech` | `[file dirname [file normalize [info script]]]/ihp-sg13g2.tech` |
| 8 | `if {[tech name] != "<tech>"} {quit -noprompt}` | yes | yes | yes |
| 9 | `source <dir>/<tech>.tcl` (device generator; `<dir>` as in step 7) | yes | yes | yes |
| 10 | key bindings `source <dir>/<tech>-BindKeys` | commented out | commented out | commented out |
| 11 | `snap lambda` | yes | yes | — |
| 12 | `set VDD …`, `set GND …`, `set SUB …` | `VPWR`, `VGND`, `VSUBS` | `VDD`, `VSS`, `VSUBS` | `VDD`, `VSS`, `sub!` |
| 13 | `addpath ${PDK_ROOT}/<tech>/libs.ref/<lib>/mag` for each standard library | 14 libraries | 9 libraries | — |

The startup files do not wrap `tech load` in `suspendall`/`resumeall`, do not set a DRC style or run `drc on`, do not read `MAGTYPE`, and do not call `magic::query_mylib_ip` or `magic::query_my_projects`. Those two procedures are defined by `common/pdk.tcl` but nothing in the PDKs calls them.

To run these files, the editor SHALL provide:
- `env` as an array of process environment variables, and `catch`, `if`, `lindex`, `info exists`;
- `file nativename`, `file normalize`, `file dirname`, `file join`, `file exists`, `file isdirectory`;
- `info script`: while a startup file or a `source`d file is being evaluated, it returns that file's path as given to the evaluator. It returns to the outer file's path when a nested `source` ends;
- `quit -noprompt` during startup: it ends the process with status 0 without running the remaining startup steps (see capability `app-startup`).

### Requirement: PDK device-script contract
A PDK device-generator script SHALL be supported when it is structured as follows. All three verified PDKs follow this structure:
- **Globals.** `TECHPATH` is set from `$env(PDK_ROOT)`, or else from the install root. `PDKPATH` is set to `${TECHPATH}/<tech>` only if it does not already exist. `PDKNAME` is set to the technology name, and `PDKNAMESPACE` is set to the namespace name (`sky130`, `gf180mcu`, `sg13g2`). The SPICE-to-layout importer uses `PDKNAMESPACE` when no library is given.
- **Window callback.** The script runs `if [catch {set Opts(callback)}] {set Opts(callback) ""}` and then `set Opts(callback) [subst {<ns>::addtechmenu \$framename; $Opts(callback)}]`. The PDK call is therefore placed *before* any existing callback text, and `$framename` stays unsubstituted until the wrapper evaluates the callback with its local `framename` (see capability `ui-gui-managers`).
- **Toolbar options.** `Opts(hidelocked)` is set to 1 and `Opts(hidespecial)` to 0.
- **Close behaviour.** If a command `closewrapper` exists, it is renamed to `closewrapperonly` and replaced by a procedure. That procedure calls `magic::quit` when `[llength [windownames all]] <= 1`, and otherwise calls `closewrapperonly`.
- **Locked layers.** `catch {tech lock fence,magnet,rotate}` hides the maze-router layers from the toolbar.
- **Namespace.** A namespace `<ns>` holds a rule dictionary `<ns>::ruleset`, built with `dict set` (layer widths, spacings and surrounds in µm), and uses `namespace path {::tcl::mathop ::tcl::mathfunc}`, so that `+ - * / < >` and math functions can be used as commands.
- **Menus.** `<ns>::addtechmenu {framename}` chooses the layout frame. If `${framename}.titlebar cget -height` raises an error, the frame is `${framename}.pane.top` (Magic 8.1.126 and later). Otherwise it is `framename`. It then builds menus with `magic::add_toolkit_menu`, `magic::add_toolkit_command` and `magic::add_toolkit_separator`. The menus are `Devices 1` (`pdk1`) and `Devices 2` (`pdk2`) for sky130 and gf180mcu, and `pdk1` only for sg13g2. It also edits the wrapper's own menus directly (Q-SCRIPT-42):
  - it appends `DRC Routing` → `drc style drc(routing)` to `<frame>.titlebar.mbuttons.drc.toolmenu`;
  - it inserts at index 4 of `<frame>.titlebar.mbuttons.file.toolmenu` an `Import SPICE` item running `<ns>::importspice`, and then a separator at index 4. `<ns>::importspice` asks for a file with `tk_getOpenFile` and calls `magic::netlist_to_layout <file> <ns>`;
  - it sets `Winopts(<framename>,cmdentry)` from `Opts(cmdentry)` (default 0) and calls `addcommandentry <framename>` when that value is 1.
- **Menu items.** A menu item either runs `magic::gencell <ns>::<device>` (opening the new-device dialog) or calls a direct drawing procedure `<ns>::<name>_draw` with no arguments. Direct drawing procedures (substrate contacts, guard rings, wells, via stacks) paint at the cursor box into the edit cell and create no generated cell.
- **Part files.** The script computes `script_path` as `[file dirname [info script]]` and sources `<tech>-util.tcl`, `-misc`, `-via`, `-fet`, `-cap`, `-res`, `-dio`, followed by `-fix` (sky130), `-bjt` (gf180mcu), or `-bjt`, `-dio`, `-fix`, `-var`, `-ind`, `-pad` (sg13g2). sg13g2 also stores the path in `sg13g2::script_path` for later use by generators.
- **Device procedures.** Each device has `<ns>::<device>_defaults|_convert|_dialog|_check|_draw`, as specified in `pcell-toolkit`. Device names follow the PDK model names, for example `sky130_fd_pr__nfet_01v8`, `nfet_03v3`, `sg13_lv_nmos`. Shared implementations live in procedures named by device family (`mos_draw`, `res_check`, `fixed_draw`, ...), and each device procedure delegates to them. Some devices lack `_check` (sg13g2 `rm6`, `rm7`); the framework tolerates this (see `pcell-toolkit`).
- **Fixed-layout devices.** Vendor BJTs, inductors, VPP capacitors and ESD cells have defaults `{nx 1 ny 1 deltax 0 deltay 0 nocell 1 xstep <µm> ystep <µm> class <class>}`. Their `_draw` runs `getcell <cell>`. When `nx > 1` or `ny > 1`, it runs `box size (xstep+deltax)um (ystep+deltay)um` followed by `array nx ny`. Values pass through `magic::spice2float`. It then runs `select cell <inst>` and `expand`, and returns the instance name. The array pitch therefore comes from the box size (see capability `cmd-selection`). See Q-SCRIPT-38 for the `pitchx`/`pitchy` keys that the framework adds when editing such a device.
Compatibility: behavioral

### Requirement: PDK helper procedures in the engine namespace
The PDK scripts define helper procedures inside the engine's `magic::` namespace. The editor SHALL let scripts define and redefine procedures there. It SHALL NOT predefine procedures with these names, because PDKs rely on their own definitions:

| Procedure | Definition (open_pdks `common/pdk.tcl`, appended to sky130/gf180mcu `<tech>.tcl`) | sg13g2 difference |
|---|---|---|
| `magic::u2l µm` | `t = tech1/tech0` from `magic::tech lambda` (integer division when both are integers); `s = round(cif scale output × 10000) / 10000.0`; returns `µm / (s × t)` | same |
| `magic::l2u λ` | `λ × s × t` | same |
| `magic::i2u v` | `s × v` | result formatted `%.3f` |
| `magic::u2i v` | `v / s` | `round(v / s)` |
| `magic::float2spice v` | picks the largest of meg, k, (none), m, u, n, p, f with v ≥ that scale, else `a`; `int(v/scale × 1000)/1000.0` followed by the suffix. The suffix is dropped when the scaled value is 0 | same |
| `magic::spice2float v ?fault 0.0?` | lowercases v and applies two single-pass `string map`s: `{um u nm n uF n nF n pF p aF a}`, then `{meg "* 1.0e6" k "* 1.0e3" m "* 1.0e-3" u "* 1.0e-6" n "* 1.0 e-9" p "* 1.0e-12" f "* 1.0e-15" a "* 1.0e-15"}`. It then runs `expr` on the result. On error it prints `Value is not numeric!` to stderr and returns `fault`. See Q-SCRIPT-40 | same |
| `magic::3digitpastdecimal v` | `int(v × 1000 + 0.5) / 1000.0` | same |
| `magic::searchcellondisk name` | `1` if `<dir>/<name>.mag` exists for any dir in `path search`, else `0` | same |
| `magic::iscellnameunique name` | `1` if `cellname list exists name` is `0` and the cell is not on disk | same |
| `magic:cellnameunique name` (single colon, a global procedure) | appends `_1`, `_2`, … until the name is unique | same |
| `magic::query_mylib_ip`, `magic::query_my_projects` | `addpath` for `~/design/ip/*/<version>/maglef` and `~/design/*/mag` directories whose `.config/techdir` link matches `TECHPATH` | absent |
| `magic::magceil v`, `magic::magfloor v` | rounding away from zero, and toward zero | sg13g2 only |

Generators use these helpers to turn dialog strings into numbers (`spice2float`) and microns into internal units (`u2i`, `i2u`). A native generator re-implementation (see `pcell-toolkit`) SHALL reproduce their exact numeric results, including the defects noted in Q-SCRIPT-40. Two PDKs loaded in one session overwrite each other's definitions (Q-SCRIPT-41).

### Requirement: Generator drawing conventions
PDK `_draw` procedures follow the conventions below. The editor SHALL give the listed commands the semantics required for them to work:
1. **Layer locks.** A draw starts with `tech unlock *` and ends with `tech revert`, so that locked types can be painted and the lock state is restored afterwards (see capability `tech-command`).
2. **Unit context.** A draw saves the input context and sets its own. sky130 and gf180mcu run `set savesnap [snap]` and `snap internal`, and restore with `snap $savesnap`; `snap` with no argument SHALL return `internal`, `lambda` or `user`. sg13g2 runs `set curunits [units]` and `units internal` (or `units microns`), and restores with `units {*}$curunits`. In both cases, un-suffixed numbers are internal units, and generators append `um` to computed micron values (for example `box grow n ${s}um`). Un-suffixed values follow `snap` only while `units` is `default` (see capability `cmd-coordinates-and-units`).
3. **Box stack.** `pushbox` and `popbox` (with no argument) are paired, 490 times or more across the three PDKs. A draw leaves the box stack as it found it.
4. **Box arithmetic.** The box is moved and grown with `box move n|s|e|w <d>`, `box grow n|s|e|w|c <d>`, `box size <w> <h>`, `box position <x> <y>`, `box values ?…?`, `box width` and `box height`.
5. **Ports.** Pins are made with `label <text> c <layer>` (justification `c`, attached to a layer), followed by `select area label` (`label` is a prefix of the special `labels`) and `port make`. Port indices are allocated automatically. sg13g2 also uses the long form `label <text> FreeSans <size> <rot> <offx> <offy> c -<layer>` (sticky). Its forms `label … c +<layer>` raise `Unknown layer` (Q-SCRIPT-39).
6. **Properties.** `property FIXED_BBOX [box values]` sets the abutment box to the box in internal units. sg13g2 sets `MASKHINTS_CONTBAR` and `MASKHINTS_PWELLBLK` with micron-suffixed coordinates (see capability `mask-hints`). Generated-cell properties are set by the framework, except for sg13g2 fixed cells (item 8).
7. **Other geometry commands.** `paint`, `erase`, `polygon <type> x1 y1 x2 y2 …` (sg13g2), `wire segment <type> <width> x1 y1 … ?-noendcap?` (sg13g2 inductors and pads), `copy n <d>` and `delete` (sg13g2 inductor), `select area <types>`, `select clear`, `select top cell`, and `getcell <cell> child 0 0` (sg13g2 bipolar).
8. **On-demand library cells (sg13g2).** Before placing a fixed cell that is not in memory (`cellname list exists <c>` is `0`), sg13g2 builds it. It saves `cellname list window` (or `cellname list self`) and `box values`, saves `tag load` and runs `tag load {}`, then `load <c> -silent` and `tech unlock *`. It sources a script that paints the cell in internal units, runs `view`, and sets `property gencell <c>`, `property library sg13g2` and, when the variable `parameters` exists, `property parameters`. ### Requirement: Technology auto-discovery from layout files
When a cell file declares a technology different from the current one, the reader is not told to ignore the mismatch, and no cell in memory contains paint, the editor SHALL search for `<tech>.tech` in these places, in order:
1. the environment variables `PDK_PATH`, `PDKPATH`, `PDK_ROOT`, `PDKROOT`;
2. `/usr/local/share/pdk`;
3. the script variables `PDK_ROOT`, `PDKROOT`, `PDK_PATH`, `PDKPATH`.

It searches each directory tree for a `magic/` subdirectory. In the scripting build, if the technology was found by any of these steps and `<dir>/<tech>.magicrc` exists, that file SHALL be evaluated as a script before the technology is loaded. The found directory SHALL be appended to the system search path, and the technology loaded. If the directory path contains `libs.tech` and no `.magicrc` was evaluated, the corresponding `libs.ref` standard-cell directories SHALL be added to the cell search path, printing `Cell path is now "<path>"`. Tag callbacks for `tech load` SHALL then run. See Q-SCRIPT-10.

### Requirement: PDK-relative paths in saved files
When writing a path into a cell file, for example the path of a child cell's file, the editor SHALL check the script variables `PDK_PATH`, `PDKPATH`, `PDK_ROOT` and `PDKROOT`, in that order. If the path starts with the value of one of them, the editor SHALL write `$<VAR><rest>`. When reading such a path, a leading `$VAR` or `${VAR}` SHALL be replaced by the script variable's value if it is defined. The variable name ends at `}`, `/`, newline, space or end of string. If the variable is not defined, the text SHALL be kept literally.

In a session started with an open_pdks rc file, the script variable `PDK_ROOT` is set by the `.magicrc` (sky130, gf180mcu) and `PDKPATH` is set by the device script to `${TECHPATH}/<tech>`. Because `PDKPATH` is checked before `PDK_ROOT`, saved library references begin with `$PDKPATH`.

### Requirement: Platform without script execution
On a platform that cannot evaluate PDK scripts (see Q-SCRIPT-1), the editor SHALL support a declarative PDK profile instead. The profile provides the effects of a PDK `.magicrc`:
- the grid rescale rule (`scalegrid 1 D` when the lambda denominator is below D);
- the Euclidean DRC setting;
- the random seed (time-based in the PDKs; a fixed value for reproducible GDS output, see Q-SCRIPT-44);
- the `ext2spice scale` setting;
- the technology file path and the expected technology name. A mismatch aborts the session, as `quit -noprompt` does;
- the snap setting;
- `VDD`/`GND`/`SUB`;
- cell search paths;
- the device library namespace, which replaces the effect of sourcing `<tech>.tcl` (see `pcell-toolkit`).

The editor SHALL apply these effects in the order the `.magicrc` would (see "PDK startup file contract"). The editor SHALL NOT silently ignore a PDK `.magicrc`. It SHALL report which statements were not applied. Device generators that are unavailable SHALL leave existing generated cells editable as ordinary cells (see `pcell-toolkit`).
Compatibility: behavioral
