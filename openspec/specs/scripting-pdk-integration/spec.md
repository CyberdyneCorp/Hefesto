# PDK Startup and Device-Script Integration

## Purpose
Specifies what open-PDK support files expect from the layout editor and what the editor does on their behalf. This covers sky130A/B, gf180mcuA-D, IHP sg13g2 and other PDKs generated by open_pdks. These PDKs ship two kinds of file:
- a startup file `<pdk>/libs.tech/magic/<pdk>.magicrc`;
- a device-generator script `<pdk>/libs.tech/magic/<pdk>.tcl`, built on the gencell framework (see `pcell-toolkit`).

This capability specifies:
- the startup ordering and command-line file handling these scripts rely on;
- the script variables and environment they read and write;
- the command surface their generators use;
- automatic technology discovery from layout files;
- the PDK path conventions in saved files.

Result formats are specified in `scripting-api`. The full startup-file search order is owned by capability `app-startup`. The PDK file contents described here come from the open_pdks templates and are not part of the Magic tree, so they are marked for verification (Q-SCRIPT-9).

## Requirements

### Requirement: Script-host startup sequence
In the scripting build, startup SHALL proceed in this order:
1. Load the engine extension.
2. Define the batch-mode console stubs and the `irsim`/`xcircuit`/`netgen`/`echo` helpers.
3. Parse the command line (next requirement).
4. If the GUI wrapper is enabled, source the wrapper and insert `-nowindow` as the first engine argument.
5. Run engine initialization with the remaining arguments. On failure, exit with status 1.
6. Source each of these optional scripts that exists in `$CAD_ROOT/magic/tcl/`, setting `Opts(<name>)=0` after each: `padlist.tcl`, `tools.tcl`, `mazeroute.tcl`, `toolkit.tcl`, `readspice.tcl`.
7. Set `auto_noexec`. Install the collision renames and the unknown handler. Import the commands globally.
8. Run the startup files (`magic::startup`). PDK `.magicrc` files execute at this point, after `toolkit.tcl` and `readspice.tcl` are available and before any layout window exists in wrapper mode.
9. Withdraw the toolkit root window if its title begins with `wish` or `magicexec`.
10. Save `drc status` and turn DRC off.
11. Open the initial window, unless a startup file already created a layout window. In wrapper mode with a display, use `openwrapper` and `techmanager initall`. In NULL graphics, use `openwindow`. Then load the command-line files (see "Command-line file arguments").
12. Print `Using technology "<tech name>", version <first element of tech version>`.
13. If no box exists, set the box to 0 0 1 1. Run `view` if files were given, else `view -9 -9 10 10`.
14. Run `crash recover` if `-r` was given.
15. Unset the temporary globals `celllist`, `nlist` and `do_recover`. Turn DRC back on if it was on.

See Q-SCRIPT-33 for `techmanager initall`.
Compatibility: behavioral

(Magic ref: tcltk/magic.tcl.in:1-470)

#### Scenario: Startup file sees the gencell toolkit
- **GIVEN** a `.magicrc` containing `source $PDKPATH/libs.tech/magic/sky130A.tcl`, which calls `magic::add_toolkit_menu` from a callback
- **WHEN** magic starts
- **THEN** `magic::gencell` SHALL already be defined when the `.magicrc` runs

#### Scenario: DRC deferred during startup
- **GIVEN** DRC was on after the startup files ran
- **WHEN** the initial cell is loaded from the command line
- **THEN** no background DRC SHALL run until the end of the startup sequence, when DRC is turned back on

### Requirement: Command-line options in the script host
The script host SHALL classify each argument with the following regular expressions, in order:

| Pattern | Action |
|---|---|
| `^-now(rap)?(per)?$` | disable the wrapper |
| `^-dnull` | disable the wrapper and pass the argument through |
| `^-r(e)?(cover)?$` | request crash recovery |
| `^-rc(file)?$` | pass through with the next argument |
| `^-d`, `^-g`, `^-m`, `^-i`, `^-T` | pass through with the next argument |
| `^-F` | pass through with the next two arguments |
| `^--version` | print `<version>.<revision>` and exit 0 |
| `^--commit` | print the commit id and exit 0 |
| `^--prefix` | print `$CAD_ROOT` and exit 0 |
| `^-D`, `^-n*` | pass through. Because `n*` may match zero characters, `^-n*` matches every remaining argument that begins with `-`, so unknown options are never treated as files |
| anything else | a file to load, also passed through |

Because the patterns are tested in this order, `-noc...` (console) is consumed by the launcher before this table applies, and `-rcfile` is matched by the `^-rc(file)?$` row and not as recovery. See Q-SCRIPT-37 for the ordering hazard with `-r`.
Compatibility: behavioral

(Magic ref: tcltk/magic.tcl.in:158-237, tcltk/magic.sh.in:33-72)

#### Scenario: PDK rcfile invocation
- **WHEN** `magic -dnull -noconsole -rcfile /pdk/sky130A/libs.tech/magic/sky130A.magicrc run.tcl` runs
- **THEN** the wrapper SHALL be disabled, the given rc file SHALL be used, and `run.tcl` SHALL be sourced after startup

### Requirement: Command-line file arguments
Each file argument SHALL be handled by its extension:

| Extension | Action |
|---|---|
| `.lef`, `.LEF` | `lef read` |
| `.def`, `.DEF` | `def read` |
| `.gds`, `.GDS`, `.gds2`, `.GDS2`, `.gdsii`, `.GDSII` | `gds read` |
| `.cif`, `.CIF` | `cif read` |
| `.tcl` | `source` |
| `.mag` or none | `load` |
| `.gz` | wrapper mode only: an inner `.gds` gives `gds read`, an inner `.mag` gives `load`, anything else prints `only compressed .mag and .gds are handled.` |
| other | print `don't know how to load file <f>` on stderr |

In wrapper mode, every non-empty extension other than `.gz` first prints `Handling file entry <f> extension <ext>`. In NULL graphics, every file prints `handling file entry <f> extension <ext>`, and `.gz` falls into "other". Files SHALL be processed in command-line order after the startup files.
Compatibility: behavioral

(Magic ref: tcltk/magic.tcl.in:363-439)

#### Scenario: Batch script argument
- **WHEN** `magic -dnull -noconsole drc.tcl` runs
- **THEN** `handling file entry drc.tcl extension .tcl` SHALL be printed and `drc.tcl` SHALL be sourced

### Requirement: Startup files are scripts
Every startup file SHALL be evaluated as a script at global scope. This includes the system pre-startup file `$CAD_ROOT/magic/sys/.initrc`, the system file `$CAD_ROOT/magic/sys/.magicrc`, the user file, the project file, and a file given by `-rcfile`. Script control flow (`if`, `catch`, `proc`, variables, `source`, `$env(...)`) is therefore available to PDK `.magicrc` files. An error in a file SHALL stop that file at the error and print `Error parsing <kind> "<file>": <message>`. Startup then continues with the next file. The system file SHALL set `GND` to `gnd!` and `VDD` to `vdd!`, and SHALL run the tool setup when `tools.tcl` was loaded. A later startup file can therefore override `VDD`, `GND` and `SUB`.
Compatibility: behavioral

(Magic ref: utils/main.c:840-1060, magic/proto.magicrc.in:319-328, magic/proto.initrc:1-4)

#### Scenario: PDK overrides power names
- **GIVEN** the PDK `.magicrc` contains `set VDD VPWR` and `set GND VGND`
- **WHEN** startup completes
- **THEN** `$VDD` SHALL be `VPWR` and `$GND` SHALL be `VGND`

#### Scenario: Error in rc file
- **GIVEN** line 3 of `.magicrc` is `frobnicate`
- **THEN** lines 4 onward of that file SHALL NOT run, the error SHALL be printed, and the editor SHALL still start

### Requirement: Typical PDK startup file contract
A PDK `.magicrc` (open_pdks template; verify against PDK, Q-SCRIPT-9) performs these steps, and the editor SHALL support each one with the semantics given in `scripting-api` and the command capabilities:
1. Print a banner with `puts stdout`.
2. Derive `PDK_ROOT` from `$env(PDK_ROOT)` or a compiled default, and set `PDKPATH` to `$PDK_ROOT/<pdk>`.
3. Wrap the technology load in `magic::suspendall` / `magic::resumeall` and run `tech load $PDKPATH/libs.tech/magic/<pdk>.tech`.
4. Set DRC options with `drc euclidean on`, `drc style drc(full)` and `drc on`.
5. Source the device generator `$PDKPATH/libs.tech/magic/<pdk>.tcl`.
6. Optionally source key bindings.
7. Set `snap lambda` or `snap internal`.
8. Set `VDD`, `GND` and `SUB`. For sky130 these are `VPWR`, `VGND` and `VSUBS`.
9. Set `MAGTYPE` from `$env(MAGTYPE)` or default to `mag`.
10. Run `addpath` for each `libs.ref/<MAGTYPE>/<lib>` or `libs.ref/<lib>/<MAGTYPE>` directory, depending on `file isdir`.
11. Make guarded calls `catch {magic::query_mylib_ip}` and `catch {magic::query_my_projects}`.

The editor SHALL provide `env` as an array of process environment variables, together with `file isdir`, `file exists`, `catch` and `info exists` semantics.
Compatibility: behavioral

(Magic ref: tcltk/wrapper.tcl:485-505, database/DBio.c:600-700)

#### Scenario: MAGTYPE default
- **GIVEN** the environment variable MAGTYPE is unset
- **WHEN** the sky130A `.magicrc` runs
- **THEN** `MAGTYPE` SHALL be `mag`, and `addpath` SHALL add the `mag` library directories (verify against PDK)

### Requirement: PDK device-script contract
A PDK device-generator script SHALL be supported when it is structured as follows (open_pdks template; verify against PDK):
- A namespace `<pdk>` (for example `sky130`, `gf180mcu`, `sg13g2`). It holds a rule dictionary `<pdk>::ruleset`, built with `dict set` (layer widths, spacings and surrounds in µm), and uses `namespace path {::tcl::mathop ::tcl::mathfunc}`.
- A global `PDKNAMESPACE` set to the namespace name. The netlist importer uses it when no library is given.
- Per-device procedures `<pdk>::<device>_defaults|_convert|_dialog|_check|_draw`, as specified in `pcell-toolkit`. Device names follow the PDK model names, for example `sky130_fd_pr__nfet_01v8` and `sky130_fd_pr__res_xhigh_po`.
- A menu procedure `<pdk>::addtechmenu {framename}`. It is registered by appending to `Opts(callback)` so that every wrapper window evaluates it with the wrapper's local `framename`. It decides between the layout frame `framename.pane.top` (Magic ≥ 8.1.126) and `framename`: it uses `framename` when `framename.titlebar` exists. It then builds menus with `magic::add_toolkit_menu`, `add_toolkit_command` and `add_toolkit_separator`.
- Fixed-layout devices, such as vendor capacitors or ESD cells, carry a `nocell` default parameter. Their `_draw` places a library cell with `getcell` (arrayed by `nx`, `ny`, `pitchx`, `pitchy`) and returns the instance name.
Compatibility: behavioral

(Magic ref: tcltk/toolkit.tcl:23-105,379-402,1642-1653, tcltk/wrapper.tcl:1495-1500)

#### Scenario: Menu registration survives multiple windows
- **GIVEN** the PDK script ran `lappend Opts(callback) {sky130::addtechmenu $framename}` (verify against PDK)
- **WHEN** two wrappers are opened
- **THEN** each window SHALL get its own device menus

### Requirement: Command surface used by device generators
The editor SHALL support each of the following command forms, with the results specified in `scripting-api`, because PDK `_draw`, `_check` and `_convert` procedures and the gencell framework call them:

| Area | Command forms |
|---|---|
| Box and units | `box values ?llx lly urx ury?`, `box size w h`, `box position x y`, `box move <dir> <d>`, `box grow <dir> <d>`, `box width`, `box height`, `units ?<type>? ?print\|noprint?`, `snap ?internal\|lambda\|user?`, `pushbox`, `popbox`, `peekbox` |
| Painting | `paint <layers>`, `erase <layers>`, `label <text> ?font size rot offx offy just layer?`, `port make ?n?`, `port <ref> index\|class\|use ?v?`, `property <key> ?value?` (including `FIXED_BBOX`, `parameter`, `device`) |
| Hierarchy | `cellname create\|delete\|list ...`, `pushstack`, `popstack`, `getcell <cell> ?orient? ?child x y?`, `identify <name>`, `select cell\|top cell\|area\|clear`, `delete`, `expand`, `array <nx> <ny>`, `array -list count\|pitch`, `instance list ...` |
| Query | `tech name\|lambda\|layer`, `cif scale out`, `what -list`, `goto`, `drc check`, `magic::display` |
| Display | `suspendall`, `resumeall`, `redraw`, `updatedisplay` |

Device generators SHALL be able to rely on these behaviors:
- coordinates without a suffix are interpreted per the current `snap` setting;
- values with suffixes `um`, `i`, `l` or `g` are converted;
- all results are plain script strings and lists.

See Q-SCRIPT-9 for the verification status of this inventory.
Compatibility: behavioral

(Magic ref: tcltk/toolkit.tcl:119-446,789-1283, tcltk/tools.tcl:122-265)

#### Scenario: Microns in a generator
- **GIVEN** `snap internal`, units `internal`, and 1 internal unit = 0.005 µm
- **WHEN** a generator runs `box size 0.17um 0.17um` and then `paint mcon`
- **THEN** the painted square SHALL be 34 × 34 internal units

### Requirement: Technology auto-discovery from layout files
When a cell file declares a technology different from the current one, the reader is not told to ignore the mismatch, and no cell in memory contains paint, the editor SHALL search for `<tech>.tech` in these places, in order:
1. the environment variables `PDK_PATH`, `PDKPATH`, `PDK_ROOT`, `PDKROOT`;
2. `/usr/local/share/pdk`;
3. the script variables `PDK_ROOT`, `PDKROOT`, `PDK_PATH`, `PDKPATH`.

It searches each directory tree for a `magic/` subdirectory. In the scripting build, if the technology was found by any of these steps and `<dir>/<tech>.magicrc` exists, that file SHALL be evaluated as a script before the technology is loaded. The found directory SHALL be appended to the system search path, and the technology loaded. If the directory path contains `libs.tech` and no `.magicrc` was evaluated, the corresponding `libs.ref` standard-cell directories SHALL be added to the cell search path, printing `Cell path is now "<path>"`. Tag callbacks for `tech load` SHALL then run. See Q-SCRIPT-10.
Compatibility: behavioral

(Magic ref: database/DBio.c:575-740)

#### Scenario: Opening a sky130 cell in a bare session
- **GIVEN** an empty session with tech `minimum`, the environment variable `PDK_ROOT=/pdk`, and `/pdk/sky130A/libs.tech/magic/sky130A.tech` present
- **WHEN** `load inv` reads a file starting `magic` / `tech sky130A`
- **THEN** technology `sky130A` SHALL be loaded and `/pdk/sky130A/libs.ref` cell paths SHALL be added (verify against Magic)

### Requirement: PDK-relative paths in saved files
When writing a path into a cell file, for example the path of a child cell's file, the editor SHALL check the script variables `PDK_PATH`, `PDKPATH`, `PDK_ROOT` and `PDKROOT`, in that order. If the path starts with the value of one of them, the editor SHALL write `$<VAR><rest>`. When reading such a path, a leading `$VAR` or `${VAR}` SHALL be replaced by the script variable's value if it is defined. The variable name ends at `}`, `/`, newline, space or end of string. If the variable is not defined, the text SHALL be kept literally.
Compatibility: exact

(Magic ref: database/DBio.c:2585-2610,6065-6090)

#### Scenario: Portable library reference
- **GIVEN** `set PDKPATH /pdk/sky130A` and a child cell read from `/pdk/sky130A/libs.ref/mag/sky130_fd_sc_hd/inv_1.mag`
- **WHEN** the parent is saved
- **THEN** the stored path SHALL begin with `$PDKPATH/libs.ref/mag/sky130_fd_sc_hd`

### Requirement: Platform without script execution
On a platform that cannot evaluate PDK scripts (see Q-SCRIPT-1), the editor SHALL support a declarative PDK profile instead. The profile provides the effects of a PDK `.magicrc`:
- the technology file path;
- DRC style and Euclidean setting;
- snap setting;
- `VDD`/`GND`/`SUB`;
- `MAGTYPE`;
- cell search paths.

The editor SHALL apply these effects in the order the `.magicrc` would. The editor SHALL NOT silently ignore a PDK `.magicrc`. It SHALL report which statements were not applied. Device generators that are unavailable SHALL leave existing generated cells editable as ordinary cells (see `pcell-toolkit`).
Compatibility: behavioral

(Magic ref: tcltk/magic.tcl.in:339-470)

- **WHEN** a session starts on iPadOS
- **THEN** `tech name` SHALL be `sky130A`, `$VDD` (or its equivalent query) SHALL be `VPWR`, and the cell search path SHALL equal the desktop session's
