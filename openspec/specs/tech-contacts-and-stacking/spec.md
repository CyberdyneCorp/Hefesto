# Technology Contacts and Stacking

## Purpose

Defines the `contact` section of a technology file (alias `images`). It covers how a type is declared a contact, its residues and the planes it touches, the `stackable` statement, how stacked contact types are generated automatically (when, their numbers, names, residues and home planes), and the residue-on-plane function that the paint tables and other capabilities use. Paint and erase behavior of contacts is specified in capability `tech-compose-and-connect`. Name lookup and type lists are specified in capability `tech-layers-and-planes`.

Terms:
- **Contact:** a type that has images on several planes. A tile of the contact type is stored on every plane in its plane set.
- **Residue:** a contact's residue on a plane is the non-contact type that would be left on that plane if the contact cut were removed.
- **User contact:** a contact declared on a contact line.
- **Stacked type:** a contact generated by `stackable`. Its residues are two user contacts, called its component contacts.

## Requirements

### Requirement: Contact declaration line

Each line of the `contact` section SHALL be a contact declaration, a `stackable` statement, or an error:

```ebnf
contact-line   = [ ( "contact" | "device" ) ] , base-type , residue , { residue }
               | "stackable" , [ base-type , [ stack-item , { stack-item } ] ] ;
stack-item     = type-name | alias-name ;          (* see "stackable statement" *)
base-type      = type-name ;                       (* single-type resolution *)
residue        = type-name ;
```

Compatibility: exact

1. **First token as a type.** The first token is first resolved as a single type name, using unique-prefix lookup and then the alias table. If it resolves, the line is a contact declaration with that base type, and all the remaining tokens are residues.
2. **Keyword `contact` or `device`.** If the first token does not resolve and equals `contact` or `device` exactly, the second token is resolved as the base type, and the tokens after it are residues. If the base type does not resolve, a noisy resolution error is reported and the line is rejected. The two keywords have the same meaning.
3. **Keyword `stackable`.** If the first token does not resolve and equals `stackable` exactly, the line is a stackable statement.
4. **Anything else.** The loader reports `Unrecognized layer (type) name "<tok>"` or `Ambiguous layer (type) name "<tok>"`, and the line is rejected.

Because step 1 resolves the first token by unique prefix, a technology with a type whose name begins with `contact`, `device` or `stackable` changes how the keyword lines are read (see Q-TECH-17).

A contact declaration needs at least one residue to pass the home-plane check in "Residue validation". A line with only a base type fails with `Contact type <t> missing a residue on its home plane`.

Declaring the same base type twice merges the residue sets and registers the contact twice (see Q-TECH-17). With `magic-compat` OFF, a first token that exactly equals `contact`, `device` or `stackable` SHALL be read as the keyword, and redeclaring a contact SHALL be an error that rejects the line.

**Init:** when the `contact` header is read, every type becomes a non-contact with an empty residue set and an empty plane set, and the contact list is emptied.

(Magic ref: database/DBtcontact.c:84-100, database/DBtcontact.c:169-270)

#### Scenario: Plain contact line
- **GIVEN** the types of the example technology in capability `tech-file-format`
- **WHEN** the contact line `pc poly metal1` is loaded
- **THEN** polycontact (15) becomes a contact with residues {polysilicon, metal1} and plane set {active, metal1}

#### Scenario: Keyword form
- **GIVEN** the same types
- **WHEN** the line `contact ndc ndiff metal1` is loaded
- **THEN** ndcontact becomes a contact with residues {ndiffusion, metal1}

### Requirement: Residue validation

For a contact declaration with base type c, whose home plane is h, the loader SHALL check the residues in order:

Compatibility: exact

1. Each residue must resolve as a single type name. On failure the loader reports a noisy resolution error and rejects the line.
2. A residue must not be a contact. On failure: `Residue type <r> is a contact itself`, and the line is rejected.
3. A residue must have a home plane. Space, for example, does not. On failure: `Residue type <r> doesn't have a home plane`, and the line is rejected.
4. No two residues may share a home plane. On failure: `Contact residues (<r>) must be on different planes`, and the line is rejected. The message names the second residue on that plane.
5. One residue must have home plane h. On failure: `Contact type <c> missing a residue on its home plane`, and the line is rejected.

When the checks pass:
- c becomes a contact.
- Its residue set is the set of residues.
- Its plane set is the set of their home planes.
- c is appended to the contact list, in declaration order.

The residues may be on any planes, which need not be adjacent.

If another user contact already has exactly the same residue set, the loader prints the informational message `Contact residues for <c> identical to those for <others>` and still accepts c. The paint-table consequences are described in capability `tech-compose-and-connect` (see Q-TECH-22).

A rejected line leaves c a non-contact.

(Magic ref: database/DBtcontact.c:514-621)

#### Scenario: Two residues on one plane
- **GIVEN** the example technology types
- **WHEN** the contact line `pc poly ndiff` is loaded
- **THEN** `Contact residues (ndiffusion) must be on different planes` is reported and the load fails

#### Scenario: Missing home-plane residue
- **GIVEN** the example types, where m2contact has home plane metal1
- **WHEN** the line `m2c poly metal2` is loaded
- **THEN** `Contact type m2contact missing a residue on its home plane` is reported and the load fails

### Requirement: stackable statement

The `stackable` statement SHALL create stacked types for pairs of contacts. It is processed with the contacts declared so far, so it must come after the contact lines it refers to. It has three forms:

Compatibility: exact

1. **`stackable` with no arguments.** For every pair (A, B) of contacts in the contact list as it stands, where A was declared before B (index m < n, both counting only entries present when the statement starts), the loader attempts to stack A with B in that order. It stops early if the type limit is reached.
2. **`stackable A`.** The loader resolves A, noisily. If A does not resolve, the line is rejected. Otherwise it attempts to stack A with every other entry in the contact list, in list order. This includes stacked types already generated, which never qualify. The pair is (A, other), with A first. If the type limit is reached, the line is rejected.
3. **`stackable A x1 x2 ...`.** The loader resolves A, noisily. If A does not resolve, the line is rejected. Then each later token is processed in order. A "last result" starts as "none":
   - If the token resolves to a type T, the loader attempts to stack (A, T), and the outcome becomes the last result. If the pair is not eligible, `Contact types <A> and <T> do not stack` is reported but the line is not rejected.
   - If the token does not resolve, it is an alias name:
     - If the last result is a newly created stacked type, the token is added to the type-name table as a non-primary name of that type. A duplicate name reports `Duplicate name: <n>`.
     - Otherwise (no attempt yet, not eligible, or already exists), the loader reports `Contact type <tok> unknown or contact missing in stackable statement`.
     - Several unresolved tokens in a row all become names of the same stacked type. Magic's code has a branch meant to report a stray unresolved token, but that branch can never run.
   - Form 3 never rejects the line.

The user manual describes the no-argument form as "overrides any other stackable statement". The code just adds the missing pairs among the contacts declared so far. Pairs that are already stacked are skipped.

(Magic ref: database/DBtcontact.c:189-252, database/DBtcontact.c:297-320)

#### Scenario: Named stacked type with legacy alias
- **GIVEN** the example contacts pc (poly, metal1), ndc (ndiff, metal1) and m2c (metal1, metal2)
- **WHEN** `stackable pc m2c pm12c` is loaded
- **THEN** stacked type 19 named `pc+m2c` is created, and `pm12c` resolves to type 19

#### Scenario: Stackable with no arguments
- **GIVEN** the contacts pc, ndc, m2c declared in that order
- **WHEN** `stackable` is loaded
- **THEN** pair (pc, ndc) is not stacked, because they share two planes
- **AND** type 19 `pc+m2c` and type 20 `ndc+m2c` are created, in that order

### Requirement: Stacking eligibility

An attempt to stack contact A with contact B, in that order, SHALL create a new stacked type only when all of these hold:

Compatibility: exact

1. A and B are both contacts.
2. Their plane sets share exactly one plane. Sharing zero planes, or two or more, makes the pair ineligible.
3. Their residue sets share at least one type. Sharing a plane without sharing a residue on it is ineligible.
4. No user contact has a residue set equal to the union of A's and B's residue sets. If one does, that explicitly declared contact already represents the stack. This outcome is "already exists", not "ineligible".
5. No stacked type already exists whose two component contacts are A and B, in either order. If one does, the outcome is also "already exists".
6. The type count is below 254. Otherwise `Too many types to generate a new contact.  Maximum=254` is reported and the outcome is "limit reached".

Stacked types never stack further. Their residues are contacts, so condition 3 never holds against a user contact.

(Magic ref: database/DBtcontact.c:338-421, database/DBtcontact.c:694-723, database/DBtechtype.c:507-530)

#### Scenario: Explicit three-plane contact suppresses stacking
- **GIVEN** the contacts pc (poly, metal1), m2c (metal1, metal2) and a user contact `pm12c poly metal1 metal2`
- **WHEN** `stackable pc m2c` is loaded
- **THEN** no stacked type is created, because user contact pm12c already has residues {poly, metal1, metal2}

### Requirement: Stacked type properties

A stacked type S created from the pair (A, B) SHALL have these properties:

Compatibility: exact

- **Number:** the next free type number. Stacked types are numbered from U (the number of user layers) upward, in creation order.
- **Name:** the single name `<short(A)>+<short(B)>`, where short() is the primary short name (see capability `tech-layers-and-planes`). This name is both the long and the short name. It is the name written to `.mag` files.
- **Contact:** S is a contact.
- **Residues (component contacts):** {A, B}.
- **Plane set:** Planes(A) ∪ Planes(B).
- **Home plane:** the home plane of the lowest-numbered type in Residues(A) ∩ Residues(B), the shared residue.
- **Contact list:** S is appended to the contact list after all contacts that existed before it.

A plain contact name in a type list also selects every stacked type built from it (see the type-list language in capability `tech-layers-and-planes`).

(Magic ref: database/DBtcontact.c:386-418, database/DBtechtype.c:507-530)

#### Scenario: Stacked properties
- **GIVEN** the example technology
- **WHEN** type 19 is inspected
- **THEN** its name is `pc+m2c`
- **AND** its residues are {polycontact, m2contact}, its plane set is {active, metal1, metal2}, and its home plane is metal1

#### Scenario: Short-name tie decides the generated name
- **GIVEN** m2contact declared as `metal1 via,m2c` instead
- **WHEN** `stackable pc m2c` creates the stacked type
- **THEN** its name is `pc+via`

### Requirement: Contact finalization and image placement

When the `contact` section ends, the loader SHALL finish the per-type data as follows:

Compatibility: exact

- **Non-contacts.** Every non-contact type t (number below N) with home plane p > 0 gets the plane set {p} and the residue set {t}. Space keeps an empty residue set.
- **Contacts on planes.** A contact appears on every plane in its plane set. A tile of a contact on any of those planes has the contact's own type number. There are no separate per-plane image types.
- **Derived tables.** The derived tables of capability `tech-layers-and-planes` are computed: Planes(t), OnPlane(p) and Home(p).

The `contact` section must be present, even if it is empty, because it is required. The paint-table initialization in the `compose` section depends on the derived tables.

(Magic ref: database/DBtcontact.c:747-805)

#### Scenario: Non-contact residue is itself
- **GIVEN** the example technology after the contact section
- **WHEN** the residue set of metal1 is requested
- **THEN** it is {metal1}

### Requirement: Residue on a plane

The function Residue(t, p) SHALL be defined as:
- For a user type t (below U), it is the member of t's residue set whose home plane is p, choosing the lowest number if several qualify. It is space if none does. For a non-contact type t on its home plane, this is t itself.
- For a stacked type t, for each component contact c in increasing type number, it is the member of c's residue set whose home plane is p, choosing the lowest number. The first component contact that has one wins. It is space if neither does.

Compatibility: exact

The full residue set of a type is defined as follows:
- For a user type, it is its residue set.
- For a stacked type, it is the union of the residue sets of its component contacts.

(Magic ref: database/DBtcontact.c:441-464, database/DBtcontact.c:952-977)

#### Scenario: Stacked residue on metal1
- **GIVEN** the example technology
- **WHEN** Residue(pc+m2c, metal1) is evaluated
- **THEN** the result is metal1, taken from component pc, the lower-numbered component, whose residue on metal1 is metal1

#### Scenario: Stacked residue on metal2
- **GIVEN** the example technology
- **WHEN** Residue(pc+m2c, metal2) is evaluated
- **THEN** the result is metal2, taken from component m2c

### Requirement: Contact lookup by planes

The system SHALL provide a "contact connecting two types" query, which wiring and routing use. For types t1 and t2, let P = Planes(t1) ∪ Planes(t2). The query returns the lowest-numbered contact, user or stacked, from 9 to N−1, whose plane set equals P exactly. If none exists, it prints `No contact type for <t1> <t2>` with the numbers, and returns "none".

Compatibility: behavioral

(Magic ref: database/DBtcontact.c:859-877)

#### Scenario: Metal1 to metal2
- **GIVEN** the example technology
- **WHEN** the contact for (metal1, metal2) is requested
- **THEN** the result is m2contact (17)
