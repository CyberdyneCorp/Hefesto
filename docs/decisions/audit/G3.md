# Audit G3: extraction, netlisting, extresist, LEF/DEF

Scope: `def-read`, `def-write`, `ext-flattening-{hierarchy,names,read}`, `extract-{capacitance,commands,devices,file-format,hierarchy,nodes-and-labels,resistance-lumped,substrate,tech-section}`, `extresist-{command,network,output}`, `lef-{read,tech-section,write}`, `netlist-{extcheck,sim,spice-devices,spice-hierarchy,spice-options}`.

All 25 specs pass `openspec validate <cap> --type spec --strict` after the edits. Mechanical checks found no dangling capability names or Q-IDs, and every requirement has a scenario, a `Compatibility:` line and a Magic ref or Hefesto decision.

Extraction defaults are consistent everywhere they appear: `extract-commands`, `extract-tech-section`, `tech-file-format` and `docs/reference/magic/circuit-extraction.md`. `all` = adjust, capacitance, coupling, lumped, length and unique. The start-up defaults add fringehalo (on when the tech format is 34 or later), labelcheck and aliases.

## Fixed

1. **extract-commands**. In the `extract cell` text, the `extract do` option list and the `resistance` synonym, the option was named `extresist-command`. It now reads `extresist`. **Why:** a global rename had turned the command and option name `extresist` into the capability name. Magic's option table (commands/CmdE.c:1097, 1104) has `extresist`.
2. **ext-flattening-read**. Three uses of "`extresist-command` overlays" (the `Short` device rule and port-short rules 4 and 5) now say "resistance-extraction overlays (`extresist on`)". **Why:** same rename damage. The netlister option is `extresist`.
3. **extresist-command**, Purpose. "the `extresist-command` command" now reads "the `extresist` command". **Why:** same rename damage.
4. **extresist-output**, Purpose. "outputs of `extresist-command`" now reads "outputs of the `extresist` command (capability `extresist-command`)". **Why:** same rename damage.
5. **extract-substrate**, Isolated substrate regions. "(owned by `extresist-command`)" now reads "(owned by capability `extresist-command`)". **Why:** makes clear that this is a capability reference, not a command name.
6. **extract-file-format**, Record order. "implementation-defined (Q-EXTRACT-7)" now names the deterministic order of `hefesto-output-determinism` (X-1) and canonicalized golden comparison. **Why:** X-1 decides a documented order for `.ext` cap and merge records. "Implementation-defined" contradicted it.
7. **extract-capacitance**, Coupling record output. The order of names and records is no longer "implementation-defined". It now refers to `hefesto-output-determinism` (X-1). **Why:** same contradiction with X-1.
8. **extract-hierarchy**, Merge records. The Compatibility qualifier now points to `hefesto-output-determinism` for record order. **Why:** X-1 applies to merge records.
9. **ext-flattening-hierarchy**, Coupling capacitance flattening. "a deterministic order" now names `hefesto-output-determinism` (X-1). **Why:** points to the one capability that owns the order.
10. **ext-flattening-read, netlist-sim, netlist-spice-devices, netlist-spice-options**. The Magic global `EFScale` is replaced by the term `S_out`. `S_out` is defined once, in ext-flattening-read "Scale record", and the other specs reference it. **Why:** convention rule 2 (no Magic globals in requirement text).
11. **ext-flattening-hierarchy**, Visit orders. The Magic struct field `def_scale` is replaced by "the definition's scale (Requirement "Scale record" of `ext-flattening-read`)". **Why:** convention rule 2.
12. **ext-flattening-hierarchy**, Container iteration order. Two additions:
    - Key bytes are now stated to be signed and sign-extended, matching `def-write` "Table enumeration order".
    - A link to Q-NETLIST-2.

    **Why:** before this, the two specs that emulate the same Magic hash disagreed by omission on bytes 0x80 and above. Q-NETLIST-2 was also not referenced anywhere.
13. **def-write**. Two references to "the extraction (EXTFLAT) area/capabilities" (in Purpose and in Net classification) now name `ext-flattening-read` and `ext-flattening-hierarchy`. **Why:** they were dangling, non-capability references.
14. **def-write and lef-write**. The magic-type-to-LEF-layer map was defined twice:
    - Ownership now sits in `lef-write` "Magic type to LEF layer name", as its Purpose states. That requirement gained the def-write details (stacked contact types, via definitions created by `lef read`) and the scenario "Via definition captures a cut type".
    - `def-write` "Magic-to-LEF layer map" is reduced to a reference.
    - `lef-write` now cites `def-write` "Table enumeration order" in two places (the layer map and the Technology layers block order), instead of an undefined "hash-table iteration order".

    **Why:** duplicate requirement, and lef-write depended on a hash order it never defined.
15. **def-write**, Net geometry discovery. Compatibility changed from `behavioral` to `exact`, with an explicit SHALL to reproduce the tile-derived order (X-1, `hefesto-output-determinism`, Q-LEFDEF-108). **Why:** X-1 lists DEF route segments as tile-order output that SHALL be byte-identical.
16. **lef-tech-section**, annotated example. The comment on `obstruction obsv1,m1 via1` said the primary type is `obsv1`. The scenario "Two types on an obstruction line" says the primary type is the lower-numbered type. The comment now states the rule. **Why:** the spec contradicted itself.
17. **def-read and lef-read**. The text for the `def nocheck`, `def datestamp` and `def writeall` messages was duplicated in def-read and lef-read. Both now reference `def-write` "def command argument validation", which owns `def` subcommand validation. **Why:** the same messages were defined in three places.
18. **extract-commands**, Purpose. The Purpose claimed to own "the tech-format-dependent fringehalo default". It now owns only the start-up value and defers the format rule to `extract-tech-section`. **Why:** two capabilities claimed ownership of the same rule.
19. **Unreferenced open questions now linked:**

## Cross-group findings

1. **simulation-netlist-preparation (lines 5 and 83) and simulation-ui-and-crossprobe (line 169).** The same `extresist` → `extresist-command` rename damage: "`extresist-command` parasitic networks", "the testbench's `extresist-command` options" and "every `extresist-command` resistor". **Suggested fix:** use `extresist` for the command, options and resistors, and keep `extresist-command` only as a capability name. Grep the whole tree for other cases.
2. **tech-file-format, "Format version gating" item 2.** It restates the fringehalo rule, which is owned by `extract-tech-section` "Fringe model default chosen from tech format". The text is consistent today. **Suggested fix:** reduce it to one sentence that references `extract-tech-section`.
3. **hefesto-ipad-feature-scope.** It lists `extract-*`, `netlist-spice-*` and `extresist-*` as included, but does not mention `netlist-sim`, `netlist-extcheck` or `ext-flattening-*`. By its own rule they are included, but `netlist-extcheck` is specified as a standalone executable with exit statuses, and iPadOS has no processes. **Suggested fix:** list these capabilities explicitly. For `extcheck`, state how invocation and exit status map onto the in-app command API, or move it to desktop-only.
4. **docs/decisions/open-questions/EXTRACT.md, Q-EXTRACT-14.** The entry says the overview `docs/reference/magic/circuit-extraction.md` wrongly puts labelcheck and aliases in `all`. The overview has since been corrected (lines 66 and 68 are right). **Suggested fix:** mark this part of the entry as done.
5. **docs/decisions/open-questions/NETLIST.md, Q-NETLIST-38.** The entry says the fracture and near-device cutting rules are "only summarized in the spec". `extresist-network` now gives pseudo-code for both ("Tile fracturing", "Near-device cutting"). **Suggested fix:** re-check the entry against the current spec and close it or narrow its scope. No spec links it.
6. **hefesto-output-determinism.** Its order rule (name, then coordinates, then type) covers "SPICE device, instance and port order", "LEF `-tech` layer blocks" and "DEF `VIAS`/`NONDEFAULTRULES`". Four G3 specs instead emulate Magic's hash order exactly. See Needs decision 1. Whichever way that decision goes, this capability or those four specs must change.

## Needs decision

1. **Hash-order emulation versus the X-1 sort order. This is the most important finding.**
   - X-1 and `hefesto-output-determinism` require hash-ordered records to be written sorted by name, then coordinates, then type.
   - Four G3 specs instead require exact emulation of Magic's string-keyed chained hash table, which gives byte-identical output:
     - `ext-flattening-hierarchy` "Container iteration order" (device, use, node-name and global tables). This drives SPICE device order, `.subckt` port numbering and instance order.
     - `def-write` "Table enumeration order" (VIAS, NONDEFAULTRULES, blockage buckets, layer map).
     - `lef-write` (`-tech` LAYER blocks, PROPERTYDEFINITIONS, SITE order, layer-map winner).
     - `netlist-spice-options` (port index assignment "in node-table iteration order").
   - The open questions disagree. Q-NETLIST-2 and Q-LEFDEF-30 recommend replicating, while X-1 cites Q-LEFDEF-30 and chose sorting.
   - In some places hash order also decides semantics, not just output order. Examples are the LEF layer-map winner (Q-LEFDEF-92) and implicit port numbering. A sort changes the result, so canonicalized comparison cannot hide the difference.
   - **Recommendation:** amend X-1 and `hefesto-output-determinism`. Where Magic's order is a pure function of string keys and insertion history, Hefesto emulates it exactly (byte-identical). The name/coordinate sort applies only to address-keyed or platform-dependent orders, such as `.ext` cap terminal order, Q-NETLIST-1, Q-NETLIST-26 and Q-NETLIST-45. Then move the hash definition, now duplicated in `def-write` and `ext-flattening-hierarchy`, into one owner and have both reference it. The owner could be `hefesto-output-determinism` or a new `magic-ordered-table` capability.
2. **Global-net and power-name settings.** The specs decide differently about the same Magic mechanism, the Tcl `globals` array and `$VDD`/`$GND`/`$SUB`:
   - `def-write` "Net classification" applies the Tcl-build rules through settings (Q-LEFDEF-102).
   - `lef-write` "Power-name source" exposes VDD/GND settings (Q-LEFDEF-44).
   - `ext-flattening-names` uses only the trailing-`!` rule and treats the Tcl array as informative (Q-NETLIST-11).
   - `netlist-spice-options` ".global" and `ext-flattening-hierarchy` and `ext-flattening-names` (the `GND` variable) leave it to configuration (Q-NETLIST-33).

   Under X-3 a Tcl interpreter exists on every platform. **Recommendation:** define one project-level "global nets / power names" setting, perhaps in `hefesto-settings`, and make all five specs reference it. Resolve Q-NETLIST-11, Q-NETLIST-33, Q-LEFDEF-44 and Q-LEFDEF-102 together.
3. **Tier-1 (always-fix) bugs still described as Magic behaviour.** Under X-2 the following are undefined behaviour or reads of uninitialized memory. Their specs should describe the corrected behaviour once each entry records `Resolution: fix`:

   | Open question | Spec | Magic behaviour |
   |---|---|---|
   | Q-NETLIST-21 | extresist-command | `.freq` value is garbage |
   | Q-NETLIST-27 | extresist-output | FastHenry z is uninitialized |
   | Q-EXTRACT-13 | extract-devices | diode range check uses uninitialized L/W |
   | Q-NETLIST-14 | netlist-sim | merge table read past its end |
   | Q-NETLIST-42 | netlist-spice-options | dangling `-o` pointer |

   Q-LEFDEF-113 (names over 255 bytes) is already written as fixed in def-write.
4. **Use-record order** (`extract-file-format` "Use records", `behavioral (order, see Q-EXTRACT-5)`). Use order comes from Magic's subcell enumeration, which is not the paint tile plane. X-1 does not classify it as either tile order or hash order. Decide whether it is reproduced exactly, as `def-write` COMPONENTS says for the same enumeration, or canonicalized.
5. **Mixed Compatibility lines.** Seventeen requirements in G3, and 38 across the repo, use qualified forms such as `exact (content); behavioral (order)`. `spec-conventions.md` §1 shows a single class. Decide whether qualified, mixed classes are allowed. If they are, document the syntax in the conventions file; if not, split those requirements.
