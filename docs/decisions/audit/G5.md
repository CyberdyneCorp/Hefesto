# Spec audit — group G5

Scope: `digital-flow-block-import`, `digital-flow-mixed-signal`, `digital-flow-results`, `digital-flow-run`, `irsim-interface`, `netlist-window`, `openaccess`, `pcell-toolkit`, `plot-output`, `plow`, `readspice`, `router-channel`, `router-gate-array`, `router-maze`, `router-maze-iroute`, `router-net2ir`, `scheme-interpreter`, `scripting-api`, `scripting-auxiliary-tools`, `scripting-pdk-integration`, `view-3d`, `wiring-tool`.

Checks run: Compatibility line, trace (Magic ref / Hefesto decision), and at least one scenario per requirement (all present). No dangling Q-IDs, decision IDs or capability references. All 22 specs pass `openspec validate <cap> --type spec --strict` after the edits.

## Fixed

1. **`scripting-api`, Purpose and "Scripting host choice is abstracted behind a command API".** The spec said Hefesto "may host the scripts in Tcl or an equivalent engine", and described a "platform where Tcl cannot be used" with an alternative mechanism. Both contradict X-3, which puts sandboxed Tcl on every platform. The spec now binds the command interface to the embedded Tcl on every platform. The GUI, the agent and plugins get identical results through the same interface. The scenario now compares Tcl with a direct command-interface call.
2. **`scripting-api`, scenario "Shared library load".** It now states that in Hefesto the built-in `load` of a `.so` returns the sandbox error, because X-3 denies native extensions.
3. **`scripting-pdk-integration`, "Platform without script execution".** This requirement assumed iPadOS has no Tcl. It is renamed "Sessions without PDK script execution" and limited to the iPadOS curated-pack fallback of `hefesto-scripting`. A declined consent is left to `hefesto-security`. Its class changed from `behavioral` (with a Magic ref) to `native` (X-3), because Magic has no counterpart. The scenario was updated, and the remaining question was logged as **Q-SCRIPT-46**.
4. **`scripting-pdk-integration`, "Technology auto-discovery from layout files".** The implicit `.magicrc` evaluation now refers to the consent rule in `hefesto-security`. The words "In the scripting build" were removed, because every Hefesto build is a scripting build.
5. **`pcell-toolkit`, Purpose and "Native generator equivalence".** The text said "a platform where PDK generator scripts cannot run (Q-SCRIPT-1)". It now says "whenever generator scripts are not run" (native fast path or curated-pack fallback). The native-generator obligation now refers to its owner, `hefesto-scripting` ("Native PCell generators validated against Tcl"). `pcell-toolkit` keeps only the detail of what identity includes.
6. **`scripting-auxiliary-tools`, "Socket command server is opt-in".** The spec now says that `socketcmd.tcl` cannot run in Hefesto, because the sandbox denies `socket`. Any remote-control equivalent is left to `hefesto-security` ("No remote command server by default").
7. **`irsim-interface`, Purpose and "Hefesto simulator integration intent".** The spec required an in-process or remote IRSIM backend on iPadOS, which contradicts X-4 and P-13 (IRSIM is desktop-only). It now says the integration is desktop-only and that iPadOS follows `hefesto-ipad-feature-scope`. The X-4 decision ref was added, and the scenario now expects `startrsim` to fail with a desktop-only diagnostic.
8. **`view-3d`, "Platform mechanism of the 3D view".** "The platform's native 3D API" contradicted P-3 (Vulkan through MoltenVK on macOS is not native). The requirement now refers to the `hefesto-rendering` interface (Vulkan on desktop, Metal on iPadOS) and names `hefesto-3d-visualization` as the owner of Hefesto's extensions.
9. **`scheme-interpreter`, Purpose.** The spec pointed to `ui-command-dispatch` for Hefesto scripting. It now points to `hefesto-scripting` and `scripting-api`, and notes the desktop-only listing.
10. **`plow`, `router-channel`, `router-gate-array`, `router-net2ir`, `netlist-window`, Purpose.** These specs did not mention that they are desktop-only. Each now has a one-line reference to P-13 and `hefesto-ipad-feature-scope`. No requirement was duplicated.
11. **`scripting-api`.** "3-D" is now "3D".
12. **Open questions.**
    - Added `Resolution:` lines to Q-SCRIPT-1 (X-3), Q-SCRIPT-10 (consent on every platform) and Q-SCRIPT-12 (`hefesto-security`, sandbox denies `socket`) in `SCRIPT.md`, and to Q-LEGACY-71 (X-4/P-13) in `LEGACY.md`. Their recommendations assumed "iPadOS has no Tcl".
    - Updated the requirement name cited in Q-SCRIPT-42.
    - Added Q-SCRIPT-46.

## Cross-group findings

1. **`hefesto-scripting` vs `pcell-toolkit` (native vs Tcl equality).** `hefesto-scripting` requires the `.mag` contents of native and Tcl output to be byte-identical. `pcell-toolkit` requires geometric identity: paint, labels, ports, properties and name. A saved `.mag` also contains a `timestamp` line, so byte identity cannot hold for cells generated at different times. Recommendation: make `hefesto-scripting` say "byte-identical except the timestamp line", or adopt the `pcell-toolkit` definition.
2. **`hefesto-3d-visualization` vs `view-3d` (z orientation).** In `view-3d`, Magic puts the top face at z = −h·s_z and the bottom face at −(h+t)·s_z (graphics/W3Dmain.c:399-400, 432-433). The "Same stack as Magic" scenario and "Mesh generation" in `hefesto-3d-visualization` say "from z = 1.0 to z = 1.5" and "between height and height + thickness". These agree in magnitude, but the sign and axis convention is not stated. Recommendation: state the axis convention in `hefesto-3d-visualization`.
3. **`reliability-visualization` vs `plot-output`.** `reliability-visualization` exports heat maps as PNG "through the plot output of `plot-output`", but `plot-output` has no PNG format, only PostScript, PNM and SVG. Recommendation: either add PNG export (native) to a Hefesto capability, or point to a different exporter.
4. **`plot-output` "SVG plot" vs `hefesto-rendering`.** In Magic, SVG output requires the Cairo display. Hefesto has no Cairo or OpenGL path (P-3), and no capability says what produces the SVG of "the window's visible contents". Recommendation: `hefesto-rendering`, or a new native requirement, should own vector export.
5. **`hefesto-ipad-feature-scope` lists `openaccess` and `scheme-interpreter` as desktop-only.** Both specs say Hefesto does not implement them, or MAY omit them, on any platform. Calling them "desktop-only" implies that the desktop has them. Recommendation: list them as "not implemented".
6. **`hefesto-security` vs `scripting-pdk-integration`.** When the user declines consent, `hefesto-security` opens the file read-only with the `minimum` tech. Before this audit, `scripting-pdk-integration` implied that a declarative profile would apply instead. The profile is now limited to curated-pack mode (see Q-SCRIPT-46).
7. **`app-startup`, `scripting-pdk-integration` and `quit -noprompt` on iPadOS.** The PDK rc guard `if {[tech name] != ...} {quit -noprompt}` "ends the process with status 0". An iPadOS app cannot quit itself. Recommendation: `app-startup` should define the iPadOS outcome, for example aborting the session and returning to the project browser.

## Needs decision

1. **Q-SCRIPT-46: is the declarative PDK profile still needed under X-3?** The options are:
   - keep it for uncurated PDKs if App Review rejects imported scripts;
   - drop it;
   - also use it when the user declines consent.
2. **`env` in the sandboxed Tcl on iPadOS.** PDK rc files and device scripts read `$env(PDK_ROOT)`, and `scripting-api` reads `CAD_ROOT` from the environment. iPadOS has no environment variables (`hefesto-files-and-pdks`). No spec defines what the sandbox's `env` array holds, for example a synthesized `PDK_ROOT` from the PDK store, matching `hefesto-pdk-manager`'s desktop rule. Owner: `hefesto-scripting`.
3. **Tk widget paths on iPadOS (Q-SCRIPT-34, Q-SCRIPT-42).** Both recommendations assume PDK scripts run only on desktop Tcl. Under X-3 the sky130, gf180mcu and sg13g2 `addtechmenu` callbacks also run on iPadOS. They use `${frame}.titlebar…` menus, `tk_getOpenFile` and `winfo`. A decision is needed on whether the SwiftUI shell intercepts them (option b) or reports them as skipped.
4. **`getnode` on iPadOS.** `irsim-interface` is desktop-only as a whole, but `getnode` is a pure node-naming query with no process involved, and it would be useful with extraction and LVS on iPad. Decide whether to split it out, or to add it to the iPadOS included set.
5. **Sandbox file access vs `scripting-api` `cd`.** The scenario "Relative cell path survives cd" uses `cd /tmp`. Under `hefesto-scripting`, file access is limited to granted paths, so the scenario is not reachable on iPadOS. Confirm whether `cd` is allowed in the sandbox and within which roots.
6. **`scripting-api` helpers `irsim`, `netgen`, `xcircuit`.** These source external Tcl packages that load native libraries, which the sandbox denies. Decide whether Hefesto defines them as no-ops with a diagnostic, maps `netgen` to the built-in LVS (P-5), or omits them.

## Terminology

- **Build vocabulary.** "Scripting build", "Tcl build" and "builds without 3D support" describe Magic's build variants. Every Hefesto build has sandboxed Tcl and 3D, so these phrases should appear only in Magic-describing (informative) text. Remaining occurrences: `scripting-pdk-integration` ("In the scripting build, startup SHALL…"), `router-maze-iroute` (`-timeout`, "scripting builds only"), `view-3d` and `plot-output` ("in builds without …").
- **Actor.** The subject varies between "Hefesto", "the editor", "the system" and "the layout engine". The scripting specs use "the editor"; the 3D, plot and router specs use "the system". Prefer "Hefesto" for product obligations, and "Magic" for informative descriptions.
- **Generators.** "PCell", "gencell", "device generator", "generated cell" and "PDK device generators" are all in use. Suggested convention: "device generator (PCell)" for the code, and "generated cell" for its output.
- **Spelling.** British spellings appear in `plot-output` (29: colour, rasterisation, …), `view-3d` (3), `router-gate-array` (2), `scheme-interpreter` (2), `openaccess`, `plow`, `router-maze-iroute`, `router-net2ir` and `scripting-pdk-integration`. The rest of the corpus uses American spelling. Exact Magic message strings must keep their original spelling.
- **Pseudo-code identifiers.** `router-channel` (`markWanted()`, `pickBest()`, `collapse()`, `makeFeasible`) and `plow` (`mustMove`, `slivType`, `farDist`) use pseudo-code names that are Magic function or local names with the prefix stripped (for example `gcrPickBest`). They are not literal C identifiers, so they were left as is. They are borderline under spec-conventions rule 2.
- **Platform names.** "Desktop app", "Linux and macOS" and "desktop" are used interchangeably. This is consistent with P-11 and needs no change.
